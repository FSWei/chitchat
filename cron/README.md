# 定时任务：谁替她跑

她的一天不是自动发生的，是**定时任务**驱动的。任务书是文件（`journal.md`、`chat-log.md`），机械操作交给脚本。这样改行为不用改代码，改代码不用重跑提示词。

## 三个任务

| 任务 | 频率 | 做什么 | 任务书 |
|---|---|---|---|
| 日记 | `0 */6 * * *` | 补写上次到现在的这一段；归档 + 蒸馏 | `journal.md` |
| 聊天记忆 | `0 */6 * * *` | 总结新消息；推进 checkpoint；归档 + 蒸馏 | `chat-log.md` |
| 备份 | 自定 | 把数据目录推到私有 git 仓（可选） | — |

## 为什么是每 6 小时

- 太勤：一天碎成十几段，日记全是「刚坐下」「又站起来了」。
- 太懒：`journal_state.py` 的最小间隔是 90 分钟，但补跑的窗口会变长，一段写六七个小时，细节全靠编。
- 6 小时 + 90 分钟水位，一天 3–5 段，正好是「上午 / 下午 / 晚上」的粒度。

## Hermes 的接法

任务本身是宿主的东西，仓库只给任务书。以 Hermes 为例（`cron/jobs.json`）：

```json
{
  "name": "日记",
  "prompt": "读取 <你的目录>/cron/journal.md 并严格照它执行；成功只回一行确认，失败报告错误原文。",
  "schedule": {"kind": "cron", "expr": "0 */6 * * *"},
  "model": "<你的模型>",
  "enabled_toolsets": ["web", "terminal", "file"],
  "deliver": "origin"
}
```

关键是 `prompt` 只有一句话：**指向任务书**。任务书改了立刻生效，不用重建任务。

## 失败要看得见

三个地方的失败长得都一样：什么都没发生。所以：

1. **任务书里每一步都要在回报里出现**——只回 `ok` 视为不合格。
2. `lifecycle.py check` 专门查「上一轮查到消息但没推进 checkpoint」，这是最典型的静默失败。
3. 补跑会**迟到**：机器关着的时候任务不会跑，开机后补跑一次，窗口比平时长得多。任务书里要允许「一段写几个小时」，并在回报里注明这是补跑。

## 时序

```
status → 判断窗口 → 取素材 → 写 → commit（水位前进）
                              ↘ 归档 → 蒸馏 → deep
```

**先写正文、后 commit。** 反过来的话，写失败时水位已经跑在前面，那段时间永久缺失。

## 坑

- **cron 会话读不到某些技能文件**：宿主可能按会话限制读文件权限，读文件用 `cat` 而不是读文件工具。
- **别用 `python3 -c` 跑长脚本**：很多宿主的安全策略直接拦。把逻辑写成 `.py` 落盘再执行。
- **别让模型自己算日期**：时区、跨日、最小间隔都交给脚本；任务书里只出现 `FROM` / `TO`。
- **模型可能在任务里加载不到人设**：任务书里写明「用 `cat` 读」，不要依赖技能自动加载。
